## 1. 最上位目的と決定【LOCK】

AKARIのBrainは、長期記憶を維持し複数プロジェクトを安全に継続するローカル統合Brainを中心に、各機能を独立した責務のソフトウェアとして連携させる。

**OpenClawによる対話受付・イベント・定期実行・既存ツール連携と、LangGraphによる作業状態・工程・中断再開・検証の管理を組み合わせ、AKARI専用の長期記憶・正本管理と接続する設計を、第一統合候補としてLOCKする。**

OpenClawをAKARIの全責務の支配者にはしない。LangGraphを万能な記憶装置とはみなさない。LLM、OpenClaw、LangGraphは将来交換可能な境界を持つ。現時点で両者の製品採用を最終確定しない。

## 2. 機能分担【設計方針LOCK】

| 領域 | 第一統合候補の責務 | 正本・権限 |
| --- | --- | --- |
| OpenClawアダプター | 対話・外部イベント受付、スケジュール起動、既存ツール接続、結果の通知 | 仕事の実行状態や正式LOCKの正本を持たない |
| LangGraphワークフロー | 作業計画の工程、処理状態、チェックポイント、中断・再開、承認待ち、結果検証 | 個別ジョブの処理状態を一元管理 |
| AKARI長期記憶・正本管理 | GitHub聖典・LOCK・資料・履歴・作業進捗・検索・有効性判定 | GitHubの正式聖典・LOCKが優先。LLMによる無承認変更は禁止 |
| 交換可能なLLM | 推論・文章生成・必要な専門処理 | 記憶の正本・権限・作業状態を所有しない |
| 安全制御境界 | 外部送信、ファイル変更、危険な実行、承認、監査 | LLMの文章上の約束ではなくコード上の強制を目指す |

具体的な通信・プロセス分割・ホストOS・機器台数は未決定。上記は**論理的な責任分担**であり、別々のPCを要件化しない。

## 3. 典型的な処理フロー【設計方針LOCK】

1. KimまたはGhostからの要求、あるいは許可済みの定期イベントを受け付ける。
2. OpenClaw側は要求を識別し、AKARIの作業受付境界へ渡す。権限・入力検証を経由する。
3. LangGraph側はジョブIDを発行または再利用し、保存済みの工程状態を取得する。同一要求の二重実行を防ぐ。
4. AKARIの記憶管理がGitHubの最新聖典・LOCK・実ファイル・変更履歴を照合し、古い仕様を現在の事実として扱わない。
5. 許可されたLLM・ツールを用いて計画・作業・検証する。危険操作や外部送信では独立した安全制御と必要なKimの承認を通す。
6. 実行結果・根拠・作業状態を保存し、必要な正式変更のみ承認済みの手続きでGitHubへ反映する。
7. OpenClaw側は結果を通知する。GhostにはBrainの意味内容を変えずに伝えるための結果・表現意図の入力を渡す。具体的な通信形式は別途定義する。

## 4. 正本と状態の一元化【LOCK】

- 正式聖典・LOCKの正本はGitHub。Dropboxは一次保存・控えであり、競合時に勝手に上書きしない。
- 個別の作業進行状態はLangGraph側（または同等の交換可能なワークフロー管理層）に一元化し、OpenClaw側で同じジョブの独立した進捗正本を作らない。
- 会話や検索用のOpenClaw内蔵メモリは補助として利用可能だが、AKARIの正式な記録・承認済みLOCKの更新権を与えない。
- 記憶には、出典、版、日時、承認状態、有効性と変更履歴を紐付け、過去の仕様の誤復活を防ぐ。
- GhostのMemory（経験）とBrainのプロジェクト長期記憶を混同しない。

## 5. 安全性・障害時動作【設計原則LOCK／具体方式未確定】

- 外部AIへ渡す内容、ファイルへの書込み、外部送信、実行権限はLLMから独立した安全制御で制限する。
- 認証情報や秘密情報をLLMプロンプト・ログ・公開GitHubへ不用意に含めない。
- 各要求にジョブID、監査ログ、実施状態、再試行識別子を付ける設計とし、再接続時の重複実行・消失を防ぐ。
- OpenClawが停止しても保存済みのジョブ状態・正式記憶を失わない。LangGraphが停止しても通知側が作業を完了したと偽らない。
- Brainが停止してもGhostとCharacterの最低限の活動継続という既存目標を変更しない。

## 6. 第一統合試験と合格条件【開発目標・未実施】

第一候補の最小接続：**OpenClaw → LangGraph → GitHub正本確認 → 状態保存・結果検証 → OpenClaw通知**。

次のすべてを確認する。

1. OpenClawからLangGraphのジョブを開始できる。
2. GitHubの最新聖典と古いLOCKを正しく区別し、廃止されたPi5/Mac前提を現行構成に復活させない。
3. 同じジョブIDで処理状態を保存し、再起動後に継続できる。
4. 重複要求で危険な処理が二重実行されない。
5. 未承認のLOCK変更と禁止された外部送信をプログラム上で拒否できる。
6. 作業結果を根拠・状態付きでOpenClawへ返し、失敗を成功と偽らない。

テストには架空の秘密情報を用い、実際の機密を流出試験に使わない。試験結果により、OpenClaw・LangGraphの採否、代替手段、境界設計を見直す。変更が既存LOCKに影響する場合はKimの承認を得る。
