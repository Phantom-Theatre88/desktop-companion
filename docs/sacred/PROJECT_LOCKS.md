# M5Stack Desktop Companion — 重要LOCK集

この文書は、聖典本文とは別に、プロジェクト全体へ常時適用する正式LOCKを短く確認するための索引である。

## LOCK 1｜最上位ゴール

M5Stackを、単なる音声AI端末ではなく、

**「机の上に常にいて、周囲を感じ、反応し、気分が変わり、少しずつ関係性が育つ相棒」**

として成立させる。

評価基準は機能数ではなく、**「そこにいる感じ」があるか**。

## LOCK 2｜親Repoと役割分担

親Repoは `stack-chan-ko` とする。

- `stack-chan-ko`：身体・生命感・RoboEyes・首モーション・タッチ／近接反応・夜モード・自発行動の基盤
- `Dotty StackChan`：ローカルASR・TTS・LLM・会話セッション・長期記憶の部品取り
- `stackchan-local`：Mac miniとのローカルLAN通信・カメラ・IMU・タッチ・サーボ・センサー抽象化の部品取り
- `M5Stack_RoboEyes`：大型2眼・瞬き・視線・目形状・表情アニメーション用の表情エンジン
- 独自中核：`Heart Engine`

## LOCK 3｜Heart Engine

LLMそのものを「心」にしない。

Heart Engineは、少なくとも以下を担当する。

- mood
- affection
- curiosity
- boredom
- sleepiness
- attention
- 感情の時間変化
- センサーイベントによる変化
- 行動選択
- 表情への反映
- 記憶との接続

LLMが停止していても、身体・感情・基本行動は生き続ける。

## LOCK 4｜実装順

Step 2〜6を完成させる前に、LLM機能をプロジェクトの中心へ置かない。

先に、

**見る → 感じる → 反応する → 気分が変わる → 自分から行動する**

を成立させ、その後に言葉を与える。

## LOCK 5｜デバッグの1回ループルール

今後のすべてのプロジェクト・実装・デバッグ作業で共通適用する。

`実行 → 修正 → 再実行` で、同じ問題または同系統の問題が**1回でも再発した時点**で局所修正を止める。

その時点で必ず、

- 壊れている層
- 設計前提
- データフロー
- 制御主体
- 資源競合
- 上位ゴールとの整合性

を根本から見直してから次の修正へ進む。

モグラ叩き型の局所修正を続けない。

## LOCK 6｜OSS・ドナー移植の適合手術

ドナー側で正常動作していることと、本体側へ適合していることは別物として扱う。

今後、OSSや既存実装から機能を取り込む場合は、単純コピーではなく必ず「適合手術」を行う。

移植前に構造差分を確認し、各機能を以下へ分類する。

1. そのまま移植可能
2. 変換層・ラッパーが必要
3. 本体側へ合わせた再実装が必要
4. 衝突するため移植禁止
5. 参考実装としてのみ利用

基本順序は、

**ドナー機能 → 構造差分確認 → 適合設計 → 変換／再実装 → 実機確認 → 既存機能との衝突確認 → Heart Engine／反射層／表情層との接続確認**

とする。

## LOCK 7｜長期プロジェクトの判断順序

すべての設計・実装・デバッグ・完成判定は、必ず以下の順で判断する。

**最終ゴール → 全体構造 → 現在の小ゴール**

小さなゴールを単体で設定してはならない。

必ず、最終ゴールから逆算した全体構造の中の一部分として設定する。

### 完成判定

- **部分完成**：全体構造の中で定義されたStep／区間の完成条件を満たした状態
- **全体完成**：聖典で定義したDesktop Companionの最終完成条件を満たした状態

部分完成をDesktop Companion全体の完成とは呼ばない。

## LOCK 8｜センサー追加の原則

センサーは、追加できるから追加するのではない。

必ず、

**「この感覚を追加すると、この子は何を感じられるようになるのか」**

を先に定義し、Heart Engineまたは身体反応へ意味を持って接続する。

カメラ、IMU、タッチ、近接、マイク、照度、温湿度などは単独機能としてではなく、Desk Bot全体の知覚系として扱う。

## LOCK 9｜知覚・神経系を考える際の上位原則

カメラ単体で「何が認識できるか」から設計しない。

先に、Desk Botが最終的に**何を感じ、どう認知し、どう反応する必要があるか**を全体構造として定義し、その後に各センサー、知覚処理、反射、Heart Engine、記憶、行動、身体出力へ役割を割り振る。

神経系も、小さなイベントを場当たり的に足して後から全体化するのではなく、最終的な知覚・神経・心・身体の全体構造を先に定義し、その一部を小さな実装単位として完成させる。

## LOCK 10｜神経系の「意味モデル」と「搬送方式」を分離する

M5Stack内部の神経規格と、M5Stack ↔ Pi5間の通信規格は、用途・制約・実装環境が異なるため同一実装へ無理に統一しない。

ただし、完全に別言語にしてはならない。

共通化するのは、

**「何を意味する情報か」という意味モデル・語彙・ID・payload定義**

とする。

例：`FACE_DETECTED`、`PERSON_PRESENT`、`HEAD_TOUCH`、`LOOK_AT`、`LOUD_SOUND`。

原則は、**語彙は共通、文法と輸送手段は別** とする。

神経プロトコルの具体仕様は、最終的な感覚・認知・反射・Heart Engine・記憶・行動・身体出力の配置と、M5Stack／Pi5の役割分担を洗い出してから確定する。

## LOCK 11｜M5Stack＋Raspberry Pi 5の脳機能分担

Desktop Companionは、M5StackとRaspberry Pi 5を単なる親機／子機として扱わず、役割の異なる脳・身体として構成する。

- M5Stack：**身体＋生命維持できる低次脳＋反射系**
- Raspberry Pi 5：**高次の感覚野＋認知脳＋言語＋長期記憶**

Pi5停止時でもM5Stack側の基本生命活動を継続する。

## LOCK 12｜視覚は2カメラ構成とする

視覚系は、M5Stack側カメラとPi5直結カメラの**2カメラ構成**を正式方針とする。

- **M5 Camera＝反射の目**
- **Pi5 Camera Module 3 Wide＝理解する目**

Pi5側高次視覚カメラは **Raspberry Pi Camera Module 3 Wide** を採用機種としてLOCKする。

M5カメラとPi5カメラで同じ制御権を競合させない。

## LOCK 13｜購入済み感覚器官・接続部品

以下をDesktop Companionの購入済み構成部品として正式登録する。

- **M5Stack Unit ToF4M / U172**：距離・接近感覚。Kimとの距離、人や物体の接近・離脱を感じるために使用する。公式仕様上は約4cm〜400cmのToF測距、I2Cアドレス `0x29`。
- **M5Stack Unit TMOS PIR / U185**：人の在席・存在・活動感覚。静止を含む人の存在感知を低次感覚として扱う。I2Cアドレス `0x5A`。
- **M5Stack Unit ENV-Pro / U169**：環境感覚。温度・湿度・気圧を基本とし、VOC、CO2相当値、IAQも将来利用可能な感覚情報として保持する。I2Cアドレス `0x77`。
- **M5Stack Unit Hub / U006**：上記3ユニットを同時接続するHY2.0-4P/Grove 1→3分岐。感覚器官そのものではなく、末梢神経の分岐部として扱う。

3つのセンサーはI2Cアドレスが異なるため、アドレス上は同一バスで共存可能。Unit Hubは3ポート直結構造であるため、実機統合時には電源・バス負荷・タイミングも確認する。

詳細な意味付けと感覚野への接続は `M5Stack Desktop Companion 感覚器官聖典 v0.1.md` を正本とする。

### Raspberry Pi 5側

- SSD：購入済み。高次認知、長期記憶、モデル、ログ等の保存基盤として使用する方向
- 高次視覚カメラ：**Raspberry Pi Camera Module 3 Wide を採用LOCK**

SSDの具体機種・容量・接続方式について、本文書で未確認の内容は推測して固定しない。
