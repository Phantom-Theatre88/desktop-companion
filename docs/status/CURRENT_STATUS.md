## 1. 最上位ゴール

M5Stackを、単なる音声AI端末ではなく、

**「机の上に常にいて、周囲を感じ、反応し、気分が変わり、少しずつ関係性が育つ相棒」**

として成立させる。

評価基準は機能数ではなく、**「そこにいる感じ」があるか**。

## 2. 現在の大きな論点

現状のDesk Bot実装は、聖典Step 0〜11へ正しく再マッピングする必要がある。

特に、Yuki由来のVision／身体系機能と、今後の正本身体である `stack-chan-ko` の統合について、単純移植ではなく「適合手術」が必要。

現在は、カメラ単体の不具合修正を続ける段階ではなく、

**知覚・神経・反射・Heart Engine・身体出力をどう接続するかの全体構造を先に定義する段階**

と判断する。

## 3. 現在確認できている実装事実

GitHub `Phantom-Theatre88/desktop-companion` の現Yuki実装には、少なくとも以下が存在する。

- 独自LVGLキャラクター表示
- 瞬き・視線・口・emotion状態
- ESP-DL顔検出
- 顔位置に応じた視線・pan/tilt追尾
- 左右のwave detection
- カメラ経路のmutex保護
- 頭タッチ・揺れ等の最近のinteraction取得
- 12個LED制御
- curiosityによる自発会話
- Xiaozhi音声ランタイム
- カメラ画像を使う高度Vision経路

ただし、コード上に存在することと、現在の実機で正常動作していることは分けて扱う。

## 4. 現在の実機上の重要な未達

### カメラ／周囲認識

現状、**「見ているが、周囲を意味として認識して身体・心へ渡せている」とは言えない。**

ベース側のカメラ認識／動作が期待どおり成立しなかったため、Yuki側Visionをドナー候補として扱った。

しかし、ドナーと本体の構造差を先に比較して適合設計を行う「適合手術」としては進めていなかった。

このため、現時点ではYuki Visionのコード単体修正を続けない。

## 6. 正式LOCKされた現在の判断

### デバッグ

`実行 → 修正 → 再実行` で同じ問題または同系統の問題が1回でも再発したら、局所修正を止めて根本解析へ切り替える。

### 適合手術

Yuki、stack-chan-ko、Dotty StackChan、stackchan-local、M5Stack_RoboEyes、その他OSSからの移植は、単純コピーで完了扱いしない。

必ず、

**構造差分確認 → 適合設計 → 変換／再実装 → 実機確認 → 衝突確認 → Heart Engine／反射層／表情層との接続確認**

を行う。

### 長期プロジェクト判断順

常に、

**最終ゴール → 全体構造 → 現在の小ゴール**

の順で判断する。

### 神経系の共通化

M5Stack内部とM5Stack ↔ Pi5の通信は、同じ用途ではないため実装・搬送方式を無理に一本化しない。

ただし、

**意味モデル・語彙・ID・payload定義は共通化する。**

原則は、

**語彙は共通、文法と輸送手段は別**

とする。

M5Stack内部は低遅延・軽量な内部イベント／APIとして実装し、M5Stack ↔ Pi5は再接続・切断・バージョン・認証・帯域を考慮した通信として設計する。

具体プロトコルは、最終的な感覚・認知・反射・Heart Engine・記憶・行動・身体出力の配置と、M5Stack／Pi5の役割分担を洗い出してから確定する。
