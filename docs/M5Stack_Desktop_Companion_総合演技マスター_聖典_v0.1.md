# 1. 外部公開資産から採用した設計知見

本マスターは既存資産をコピーするものではなく、公開されているロボット表現ライブラリ／HRI研究を**チェックリストと設計原則**として参照した。

## 1.1 FluxGarage RoboEyes
- 目幅・高さ・角丸・両目間隔を独立パラメーター化。
- Mood と Gaze、Blink、Idle、Curiosity、Flicker、Confused、Laugh を分離。
- 自動瞬きとランダム視線で「何もしていない時間」に生命感を作る。
- 本マスターでは、感情そのものと再利用可能なFXを分離する考え方へ反映。

Source: https://github.com/FluxGarage/RoboEyes

## 1.2 Kaia Face
- 32種の表情語彙を公開。
- gaze speed、wink、widen、eye-roll等を表情から独立したアニメーションとして制御。
- apologetic / awkward / embarrassed / flustered / mischievous / starstruck / winking 等を、対人ニュアンスの抜け確認に利用。

Source: https://github.com/kaiaai/kaia-face.js

## 1.3 Procedural Expression Library
- 固定画像列ではなく、目形状を手続き生成し、表情間を補間して遷移。
- 非対称表情にも対応。
- 本マスターの「固定動画を大量に持たず、パラメーターと補間で演技を構成する」方針を補強。

Source: https://github.com/ggldnl/Procedural-Expression-Library

## 1.4 M5Stack RoboEyes
- M5Stack + M5GFX 上で RoboEyes の構造を実装した公開例。
- M5Stack系画面でも mood / gaze / blink / idle / flicker が成立することを確認する参考資産。

Source: https://github.com/Harrison-Xu/M5Stack_RoboEyes

## 1.5 HRI研究：首動作とタイミング
- ロボットの首動作は、無動作より animacy / likeability / anthropomorphism / perceived intelligence を高める傾向が報告されている。
- 発話と同時に動くより、**発話より先に首が動き始める**条件の方が自然さの評価が高かった。
- 本マスターでは TimingParameters を「見た目の補間」だけでなく、会話ターン演技にも使う。

Source: Lee & Hahn, Effect of Robot Head Movement and its Timing on Human-Robot Interaction, International Journal of Social Robotics (2025)
https://link.springer.com/article/10.1007/s12369-024-01196-0

# 2. 統合マスターの読み方

各演技は以下を横断して定義する。

**演技ID → 目表情 → 首2軸 → 画面描写 → イベント → FX → 主パラメーター**

数値はまだ固定しない。  
このv0.1では「どの部品を使って演技を作るか」をLOCK対象とし、実角度・速度・RGB・時間値は実機検証後に割り当てる。

# 6. 会話タイミング規則

公開HRI研究を踏まえ、会話中の演技について以下を正式方針とする。

1. 発話に伴う首・視線モーションは、可能な場合 **TTS開始より少し先行**させる。
2. 返答生成待ち時間を「無表情停止」にせず、C03/C17/H04等の演技で埋める。
3. 発話中は大きな動きを連発せず、視線・小うなずき・微動を主体とする。
4. ユーザーの発話中は、追従と聞いている演技を優先する。
5. 反射動作はLLM応答を待たず、Reflex Layerから即時発火できる設計とする。

# 7. マスター運用規則

- 個別聖典は削除しない。総合マスターはそれらを置き換えるものではなく**索引＋演技レシピ正本**。
- 目表情番号を変更する場合は、総合マスター側の参照も更新する。
- Event ID / Parameter ID は既存聖典のIDをそのまま使う。
- 新規演技追加時は、まず既存演技＋FX＋Eventの組み合わせで表現できないか確認する。
- 固定動画の追加は最後の手段とする。
- 「何もしない」「微細に動く」「視線だけ動く」を有効な演技として維持する。
- 画面演出は物理2軸の不足を補うが、過剰な疑似3D表現は避ける。
- 目が主役。首・画面・Eventは意味を読みやすくするための補助。
- Heart Engineは演技IDを選択し、Renderer/Servo/Event層がレシピを展開する構造を目標とする。
